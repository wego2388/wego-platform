## القرار المؤقت لحين تجهيز Paymob

**المقترح الافتراضي: كتالوج وأسعار معتمدة + طلب عبر واتساب + تأكيد من المكتب.**
ليس حجزًا مؤكدًا بمجرد الضغط، ولا دفعًا ناجحًا، ولا حجز سعة تلقائيًا.

1. يرى الزائر الرحلة والسعر المعتمد وسياسة الإلغاء والمعلومات المتاحة.
2. زر واضح مثل «اطلب الحجز عبر واتساب» باللغات الأربع، مع تنبيه أن الموعد
   والسعة يحتاجان تأكيدًا من المكتب وأن الدفع الإلكتروني غير متاح الآن.
3. الرسالة المبدئية تحمل اسم/معرّف الرحلة، اليوم والفترة وعدد المشاركين
   إن اختارهم الزائر؛ لا نضع اسمًا/هاتفًا/إيميلًا أو token من نموذج في URL.
4. المكتب يراجع السعة قبل التأكيد؛ ظهور عدد الأماكن على الموقع ليس ضمانًا
   بأن المحادثة حجزتها. لا زر «تم الدفع» ولا voucher نهائي لطلب غير مؤكد.
5. تسجيل حجز المكتب وتأكيده داخل ERP يعتمد على حزمة الحجز اليدوي التالية
   ومراجعتها، ولا يُستبدل بجدول خارجي يصير سلطة حجز ثانية.

### قبول التنفيذ — الحزمة مكتملة محليًا، لا اعتماد نشر بعد

- [x] وضع تشغيل صريح وآمن لحين تفعيل البوابة، منفصل عن mock الاختبارات.
  backend يبدأ بدون مفاتيح Paymob فقط في هذا الوضع المعتمد، ويمنع بدء الدفع
  والاسترداد بوضوح؛ لا نتيجة Success مصطنعة ولا bypass لـHMAC أو الصلاحيات.
- [x] العقد ومصدر حالة المبيعات يوضحان للواجهة الوضع الفعلي؛ لا تعتمد الحماية
  على إخفاء زر أو browser config وحده.
- [x] إيقاف checkout في كل entry point، بما فيه العودة لحجز/صفحة دفع قديمة.
- [x] إن وُجدت مدفوعات تاريخية أو webhooks قيد الوصول، تُراجع آلية استقبالها
  وتسويتها قبل تعطيل أي provider؛ لا حذف أسرار HMAC لازمة أو تجاهل سجل الدفع.
- [x] ربط CTA بالرقم الموجود المعتمد وعدم إضافة PII إلى analytics/UTM أو
  URL؛ أحداث enquiry لا تتحول إلى purchase.
- [!] ساعات/مسؤول التأكيد ومدة الرد تحتاج اعتماد محمد قبل الإطلاق.
- [x] اختبارات backend/HTTP/permissions وعزل، واختبارات الموقع باللغات الأربع.
- [x] مراجعة Tier 1 مستقلة READY: يتغير تركيب payment adapter وحدود التشغيل، لذلك
  لا يُدخل هذا بصمت في حزمة ترجمة ERP.

**التحصيل المؤجل:** cash/تحويل/رابط خارجي ليست طرقًا معتمدة تلقائيًا. نحتاج
تحديد الطريقة والعملة ووقت التحصيل ومن يعتمدها، ثم عقد وسجل تحصيل وتسوية
ومنع التكرار. حتى ذلك، الطلب «بانتظار تأكيد المكتب»، وليس `PAID`، ولا يصدر
إيصال تحصيل. لا تُمدّد مهلة NEW أو تحجز السعة بلا قاعدة تشغيل موثقة.

### الانتقال لاحقًا إلى Paymob

- [ ] وصول مفاتيح sandbox في إعداد خاص آمن، دون إرسالها في المحادثة أو Git.
- [ ] اختبار نجاح/رفض/timeout/webhook مكرر ومتأخر/refund/reconciliation فعلي.
- [ ] اعتماد عملة/أساليب الدفع وcallbacks والدومين، ثم مفاتيح production.
- [ ] تفعيل خاضع للصلاحية والمراقبة مع rollback واضح إلى enquiries؛ لا نعتمد
  رجوع المتصفح كحقيقة دفع، ولا نعيد تصنيف الطلبات القديمة تلقائيًا كمدفوعة.

## الصور من الداشبورد — مواصفة البداية التاريخية

> **تحديث لاحق في 5 أكتوبر:** محرر الرحلة ورفع الصور وشاشة الفئات وAPI
> والتخزين نفذت واختباراتها المحلية ناجحة. الجدول/الوصف الأصلي أدناه يحفظان
> نطاق البداية، وليس الحكم الحالي. قبول MEDIA وDB+media restore وبوابات
> الإصدار ما زالت مفتوحة. المرجع الحي:
> `2026-10-05_CATALOG_MEDIA_SAFE_CHECKPOINT_AR.md`.

حاليًا API لمحتوى الرحلات يدعم **مسارات** media وحقوق الاستخدام والمراجعة
والنشر؛ هذا لا يساوي رفع ملف من الجهاز. Tours ERP الحالية قائمة/تفعيل/مواعيد،
وليست محرر محتوى أو uploader. الفئات الحالية enum ثابت، وتصميمها في الموقع
يستخدم ألوانًا وأيقونات. رفع صورة فئة لا يعني إنشاء نوع رحلة أو فئة جديدة.

### نطاق أول إصدار مقترح

- [ ] محرر رحلة EN/AR للمكتب: صورة غلاف، gallery، ترتيب، alt مناسب للغات
  المنشورة، معاينة، حالة draft/approved/published، وحذف/استبدال آمن.
- [ ] صور غلاف مستقلة للفئات الحالية: DESERT/SEA/CULTURAL/SHOWS/TRANSFERS،
  بدون اختراع فئات أو أسعار أو تغيير enum بمجرد رفع الصورة.
- [ ] نوع «خدمة» يُربط بالكيان الموجود إن كان رحلة/انتقالًا في الكتالوج؛
  أي خدمة غير ممثلة في domain تحتاج نطاقًا منفصلًا، لا تخزينًا مبهمًا.
- [ ] عقد upload مصرح، محدود الحجم والأبعاد/عدد pixels والنوع، وفحص decode
  حقيقي على الخادم؛ لا الثقة في extension أو MIME القادم من المتصفح.
- [ ] إزالة EXIF/الموقع والبيانات غير المطلوبة، وإعادة ترميز الصور إلى ملفات
  صالحة؛ لا SVG/HTML/ملفات تنفيذية، ولا path traversal أو arbitrary URL fetch.
- [ ] أسماء ومسارات ينشئها الخادم، كتابة ذرية، فشل لا يترك صورة منشورة ناقصة،
  وعدم إتاحة original غير معتمد للجمهور. إعادة الطلب لا تخلق مراجع بلا نهاية.
- [ ] storage دائم خاص بإصدار Safari، خارج writable container layer؛ volume
  أو object storage معتمد لاحقًا، backup/restore للصور مع قاعدة البيانات.
  الـbackend الحالي read-only؛ لا نلغيه عالميًا لكي نسهّل الرفع.
- [ ] تحويلات responsive مع width/height، cover/gallery، lazy loading تحت
  fold، وعدم كسر cache أو تحميل الأصل الكبير لكل card.
- [ ] مراجعة حقوق الصورة وموافقة الأشخاص إن وُجدوا؛ رفع ملف لا يمنح حقوقه
  تلقائيًا. إعادة استخدام قواعد approve/publish الحالية دون تجاوزها.
- [ ] عدم حذف صورة ما زالت مرجعية في محتوى منشور؛ خطة orphan cleanup
  قابلة للمراجعة، وليست مسحًا شاملًا أو حذف صور محمد الأصلية.
- [ ] اختبارات صلاحيات، ملفات مزيفة/ضخمة/تالفة، مسارات، تعارض revision،
  failed upload، publish، backup/restore، EN/AR ومقاسات الشاشات.
- [ ] Tier 1: APIs مصرح بها وتخزين/نشر ملفات وحقوق؛ لا تنفيذ قبل نطاق ومراجعة.

الصور يمكن أن تأتي لاحقًا، لكن لا تُنشر صورة mock كأنها تجربة فعلية. المكوّن
يستخدم fallback واضحًا عند عدم وجود صورة، والـcontent readiness يظل ناقصًا.

## بوابة «جاهز للرفع» التي سأستخدمها

- [ ] scope الإصدار واضح: enquiries فقط أم دفع إلكتروني فعلي؟ ويظهر ذلك
  في الواجهة والتشغيل والاختبارات والتسليم، دون خلط «طلب» بـ«حجز مؤكد».
- [ ] كل وظائف الإصدار المختار مكتملة، ولا صفحات تشغيل أساسية غير مترجمة.
- [ ] build/lint/typecheck/contracts/domain/integration/E2E/audit ناجحة على
  نفس الشجرة النهائية؛ fixtures منفصلة عن دليل backend وPaymob الفعلي.
- [ ] مراجعة Tier 1 مستقلة بصفر موانع لأي تعديل دفع/صلاحيات/migrations/uploads.
- [ ] Foundry lock/profile/migrations والحزمة المستقلة متطابقة وحتمية؛ لا
  Resort OS أو مشروع عميل آخر أو بياناته داخل حزمة Safari.
- [ ] Compose الإنتاج يبدأ **بالوضع المختار** مع رفض mocks/placeholders؛
  public لا يعرض staff API، وERP محمي وغير مفهرس، والـDB غير مكشوف للإنترنت.
- [ ] image architecture توافق الـVPS. البناء المحلي أدرج sharp لـlinux-x64؛
  لو السيرفر ARM لا ننسخ هذا `.output` وندعي التوافق، بل نبني ونختبر artifact
  مناسبًا لمعمارية الهدف.
- [ ] HTTPS وcanonical/hreflang والـstaff origin والتواصل صحيحة على الدومين.
- [ ] حساب أول مدير يُنشأ بطريقة موثقة، password rotation وصلاحيات واضحة؛
  لا حسابات fixtures أو أسرار افتراضية في release.
- [ ] صور وDB محفوظتان خارج container، backup مشفر خارج السيرفر، واسترجاع
  مجرّب، monitoring وقرارات pause/rollback واضحة.
- [ ] دليل إصدار: الملفات/الأوامر والنتائج وموانع/حدود، tag/digest ثابت
  بعد تفويض commit/build release، بدون اعتبار worktree dirty إصدارًا نهائيًا.
- [!] UAT وموافقة محمد على الصور والحقائق القانونية وطريقة التأكيد والنشر.

لا نطلب مفاتيح Paymob للنشر بوضع enquiries بعد تنفيذ واعتماد وضع آمن؛
أما تشغيل الدفع الإلكتروني أو وجود مدفوعات تاريخية فيحتاج إعداداته الكاملة.
قبول الحزمة المحلية لا يساوي اجتياز باقي بوابات الإطلاق.
